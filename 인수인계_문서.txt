========================================

작성일: 2024년
문서 버전: 1.0


1. 호스팅 방식
========================================

1.1 서버 구성
본 시스템은 ngrok을 이용한 터널링 방식으로 호스팅되며, 다음과 같이 구성되어 있습니다.
- 서버 실행 포트: localhost 14723
- 외부 접근: ngrok 터널링을 통한 인터넷 공개
- ngrok 설정 파일: ngrok.sh 스크립트 (ngrok 인증 토큰 설정 및 포트 14723 노출 명령 포함)

1.2 서버 실행 절차
본 시스템의 서버 실행 절차는 다음과 같습니다.
(1) api.py 실행: FastAPI 서버 구동
(2) ngrok.sh 실행: 별도 터미널에서 외부 접근 활성화

1.3 접근 주소
- 로컬 접근: http://localhost:14723
- 외부 접근: ngrok 실행 시 생성되는 동적 URL 사용
- API 문서: http://localhost:14723/docs (Swagger UI 자동 생성)


2. 시스템 개요
========================================

2.1 시스템 목적
본 시스템은 미술관 전시 환경을 위한 AI 기반 큐레이션 나레이션 생성 및 터치 인식 API로서, 관람객에게 맞춤형 작품 설명을 제공합니다.

2.2 기술 스택
- 개발 언어: Python 3.10 이상
- 웹 프레임워크: FastAPI
- LLM 모델: OpenAI GPT-4o-mini
- 의존성 관리: requirements.txt

2.3 핵심 기능
본 시스템은 다음 두 가지 핵심 기능을 제공합니다.

(1) 큐레이션 나레이션 생성 기능
- 6가지 큐레이션 타입을 통한 작품 설명 생성
- 관람객의 관람 맥락과 질문에 따른 발화 스타일 선택
- TTS(음성 합성) 최적화 적용
- 이전 대화 기록(memory)을 통한 중복 방지 및 새로운 관점 제공

(2) 터치 기반 객체 인식 기능
- 작품 특정 위치 터치 시 객체 자동 인식
- SAM 모델 및 Ray-casting 알고리즘 기반 객체 판별
- LLM을 통한 간결한 설명 자동 생성

2.4 주요 파일 구조
- api.py: FastAPI 기반 메인 API 서버 (모든 엔드포인트 정의)
- curation_types.py: 6가지 큐레이션 타입 로직 구현
- touch_recognition.py: 터치 좌표 기반 객체 인식 로직
- client.py: API 테스트용 클라이언트 스크립트
- prompts/: 큐레이션 타입별 LLM 프롬프트 템플릿
- assets/: 작품 이미지, 텍스트 정보, 비교 데이터
- vision/: 마스크 데이터, 바운딩 박스, 어노테이션 정보


3. 미술작품
========================================

3.1 작품 현황
본 시스템은 총 10개의 서양 명화를 다루며, 각 작품에 대해 한국어 및 영어 작품명 매핑, 설명 텍스트, 비전 인식 데이터가 준비되어 있습니다.

3.2 작품 목록 및 주요 정보

1. 프리마베라 (Primavera)
   - 작가: 산드로 보티첼리
   - 시대: 르네상스
   - 주제: 봄의 도래와 재생, 신화 속 인물들

2. 비너스의 탄생 (The Birth of Venus)
   - 작가: 산드로 보티첼리
   - 주제: 사랑과 아름다움의 여신 탄생 장면

3. 파리스의 심판 (The Judgment of Paris)
   - 주제: 그리스 신화, 세 여신 중 최고 미인 선택

4. 아담의 창조 (The Creation of Adam)
   - 작가: 미켈란젤로
   - 위치: 바티칸 시스티나 성당 천장 프레스코화
   - 주제: 신이 아담에게 생명을 부여하는 순간

5. 최후의 만찬 (The Last Supper)
   - 작가: 레오나르도 다 빈치
   - 주제: 예수와 제자들의 마지막 식사

6. 성 마태를 부르심 (The Calling of Saint Matthew)
   - 작가: 카라바조
   - 스타일: 바로크 회화, 극적인 명암 대비

7. 아테네 학당 (The School of Athens)
   - 작가: 라파엘로
   - 주제: 고대 그리스 철학자들의 모임

8. 회화의 기술 (The Art of Painting)
   - 작가: 요하네스 베르메르
   - 시대: 네덜란드 황금기
   - 주제: 화가의 작업 과정

9. 시녀들 (Las Meninas)
   - 작가: 디에고 벨라스케스
   - 특징: 복잡한 시점 구조, 화가 자신 포함

10. 야경 (The Night Watch)
    - 작가: 렘브란트
    - 주제: 암스테르담 시민 방위대, 역동적 구도

3.3 데이터 저장 위치
- 작품 설명 텍스트: assets/llm/document/
- 작품 이미지: assets/artwork_images/, vision/artwork_images/
- 작품 비교 데이터: assets/llm/transformed_pair.json


4. 큐레이션 유형
========================================

4.1 개요
본 시스템은 관람객과의 다양한 상호작용 시나리오에 대응하기 위해 6가지 큐레이션 타입을 제공하며, 각 타입은 발화 목적, 분량, 구조가 명확하게 정의되어 있습니다.

4.2 큐레이션 타입별 상세

타입 1: 핵심설명
- 목적: 작품 이해의 출발점 제공
- 분량: 120자 이상 170자 이하
- 구성: 조형적 특징(구도, 색채) + 작품 의미
- 대상: 작품을 처음 보는 관람객

타입 2: 질문응답 flat-1 (정보제공)
- 목적: 간결한 정보 제공 및 추가 대화 유도
- 분량: 최대 3문장
- 구성: 질문 확인 1문장 + 답변 1-2문장 + 선택지 1문장
- 특징: 전문용어 최소화, 일반인 이해 가능한 표현

타입 3: 질문응답 flat-2 (단순비교)
- 목적: 작품 간 연결고리 형성
- 분량: 2문장
- 구성: 공통점 + 차이점 (1문장) + 선택지 (1문장)
- 필수 파라미터: related_artwork

타입 4: 질문응답 deep-0 (정보제공 심화)
- 목적: 역사적, 문화적, 철학적 배경 전달
- 분량: 정확히 3문장
- 구성: 제작 시기 + 예술 사조 + 작가 정보 + 시대적/철학적 컨텍스트

타입 5: 질문응답 deep-1 (정보제공 및 인상 나누기)
- 목적: 수동적 감상 → 능동적 참여 전환
- 분량: 정확히 4문장
- 구성: 배경지식 3문장 + 관람객 느낌 묻는 열린 질문 1문장

타입 6: 질문응답 deep-2 (연관작품 읽기 및 나만의 작품읽기)
- 목적: 개인적 경험과 가치관 연결 유도
- 분량: 정확히 4문장
- 구성: 타인의견 1문장 + 조형 특징 및 연관작품 비교 + 관계짓기 질문 1문장
- 특징: 가장 개인적이고 성찰적인 타입

4.3 공통 규칙
모든 큐레이션 타입은 다음 공통 규칙을 적용합니다.

(1) TTS 최적화
- 자연스러운 구어체 작성
- 따옴표, 괄호, 특수기호 금지
- 종결어미: 반드시 니다 체 사용
- 작품명: 한국어로 언급

(2) 중복 방지 메커니즘
- 이전 설명 내용 반복 최소화
- 필요 시 "앞서 언급했듯"으로 간단히 언급

(3) 질문 처리
- 관람객 질문이 있는 경우, 먼저 1문장으로 간단히 답변 후 원래 타입 응답 제공


5. 각 큐레이션 유형별 프롬프트
========================================

5.1 프롬프트 관리 방식
각 큐레이션 타입의 프롬프트는 prompts 디렉토리에 별도 파일로 관리되며, Python format 메서드를 이용한 템플릿 형식으로 작성되어 있습니다. 실행 시 작품명, 메모리, 질문 등의 변수가 동적으로 삽입됩니다.

5.2 타입별 프롬프트 상세

타입 1 (prompt_1.txt)
- 주요 지시사항: 작품 핵심 주제와 맥락 간결 설명
- 분량 제약: 120자 이상 170자 이하
- 내용 요구: 조형적 특징(구도, 색채) + 작품 의미
- 적용 규칙: TTS 최적화, 중복 방지

타입 2 (prompt_2.txt)
- 주요 지시사항: 핵심 정보 1문장 제공 + 선택지 1문장 제시
- 분량 제약: 최대 2문장
- 특징: 전문용어 최소화, 객관적 사실 중심
- 적용 규칙: TTS 최적화, 중복 방지

타입 3 (prompt_3.txt)
- 주요 지시사항: 공통점 1개 + 차이점 1개 언급 + 선택지 제시
- 구성: 한 문장 비교(공통점→차이점) + 선택지 1문장
- 데이터 활용: transformed_pair.json의 comparison_context 포함 가능
- 적용 규칙: 일반적 표현 사용, 수치/전문용어 과다 금지

타입 4 (prompt_4.txt)
- 주요 지시사항: 배경지식 정확히 3문장으로 설명
- 포함 내용: 제작 시기, 예술 사조, 작가 정보, 시대적/철학적 컨텍스트
- 구성 원칙: 시간순 또는 논리적 순서, 사실 중심 객관적 서술

타입 5 (prompt_5.txt)
- 주요 지시사항: 배경지식 3문장 + 느낌 묻는 열린 질문 1문장
- 분량: 정확히 4문장
- 톤: 친근하고 중립적
- 질문 요구사항: 예/아니오로 답변 불가능한 열린 질문

타입 6 (prompt_6.txt)
- 주요 지시사항: 타인의견 + 조형 특징 및 연관작품 비교 + 관계짓기 질문
- 분량: 정확히 4문장
- 톤: 긍정적이고 중립적
- 연관 작품 처리: 명시되지 않으면 viewed_artworks에서 자동 선택

5.3 보조 프롬프트
- prompt_question_answer.txt: 관람객 질문에 대한 간단한 1문장 답변 생성용
- TTS 최적화 및 중복 방지 규칙 동일 적용


6. API 엔드포인트
========================================

6.1 개요
본 시스템은 FastAPI 기반으로 구현되었으며, RESTful API 방식의 주요 엔드포인트를 제공합니다.

6.2 엔드포인트 목록

GET /
- 기능: 웹 인터페이스 또는 API 정보 반환
- 응답: static/index.html 파일 또는 JSON 형식 API 정보

GET /ping
- 기능: 서버 상태 확인
- 응답: pong 메시지, CurationTypes 및 TouchRecognition 로드 상태

GET /artworks
- 기능: 사용 가능한 작품 목록 조회
- 응답: 10개 작품의 한국어 이름 배열

POST /curation
- 기능: 큐레이션 나레이션 생성 (메인 엔드포인트)
- 요청 필드:
  * curation_type (필수): 1-6 사이 정수
  * art_name (필수): 작품명
  * memory (선택): 이전 대화 기록, 기본값 ""
  * viewed_artworks (선택): 이미 본 작품 목록
  * question (선택): 관람객 질문
  * related_artwork (조건부): 타입 3 필수, 타입 6 선택
- 응답: response 필드에 생성된 나레이션 텍스트

POST /touch
- 기능: 터치 좌표 기반 객체 인식 및 설명 생성
- 요청 필드:
  * art_name (필수): 작품명
  * x (필수): 정규화된 x 좌표 (0-1, 0=왼쪽, 1=오른쪽)
  * y (필수): 정규화된 y 좌표 (0-1, 0=위, 1=아래)
- 응답 (객체 발견 시): found=true, mask_id, object_name, object_info, description, art_name, art_name_en
- 응답 (객체 없음): found=false, message

POST /objects
- 기능: 작품의 모든 객체 목록 조회
- 요청 필드: art_name (필수)
- 응답: art_name, art_name_en, object_count, objects 배열

6.3 에러 처리
- 400 Bad Request: 잘못된 파라미터
- 422 Unprocessable Entity: 유효성 검증 실패
- 500 Internal Server Error: 서버 내부 오류
- 모든 에러 응답: detail 필드에 에러 메시지 포함


7. 비전 인식기술
========================================

7.1 개요
비전 인식 시스템은 관람객이 작품의 특정 부분을 터치할 때 해당 위치의 객체를 자동으로 인식하고 설명을 제공하는 기능입니다. 전처리 과정과 실시간 인식 로직으로 구성됩니다.

7.2 핵심 기술
- SAM (Segment Anything Model): 페이스북 리서치 개발의 이미지 세그멘테이션 모델
- Ray-casting 알고리즘: 점과 폴리곤의 포함 관계 판별 알고리즘
- 본 시스템에서는 SAM 모델을 사용하여 세그멘테이션 마스크를 생성하고, Ray-casting으로 객체 판별을 수행합니다.

7.3 구축 워크플로우
비전 인식 시스템 구축은 다음 단계로 진행됩니다.

(1) SAM 모델 다운로드
- 출처: 페이스북 리서치 GitHub 저장소
- 모델: ViT-H SAM 모델
- 저장 위치: segment-anything 디렉토리

(2) 바운딩 박스 어노테이션
- 스크립트: get_box.py
- 작업 방식: 수작업으로 설명할 가치가 있는 객체에 바운딩 박스 표시
- 저장 위치: vision/boxes/작품명.json

(3) 세그멘테이션 마스크 생성
- 스크립트: box_to_seg.py --artwork_name "작품명"
- 처리: SAM 모델이 바운딩 박스를 입력받아 정밀한 마스크 생성

(4) 컨투어 변환
- 스크립트: contour_visualize.py --artwork_name "작품명"
- 목적: 용량 최적화 (마스크 배열 → 경계선 좌표만 저장)

(5) 마스크 어노테이션
- 저장 위치: vision/mask_annotation/작품명.json
- 내용: 각 마스크의 이름 및 설명
- 참고: 마스크 설명은 ChatGPT 등 LLM 활용 가능

(6) 시뮬레이션 테스트
- 스크립트: contour_gui.py --artwork_name "작품명"
- 목적: GUI를 통한 터치 인식 동작 확인

7.4 실시간 객체 인식 로직
TouchRecognition 클래스(touch_recognition.py)에서 구현되며, 처리 절차는 다음과 같습니다.

(1) 좌표 변환: 정규화 좌표(0-1) → 픽셀 좌표 (이미지 원본 크기 기준)
(2) 마스크 데이터 로드: 작품별 컨투어 좌표, 이름, 설명 포함
(3) 객체 판별: Ray-casting 알고리즘으로 각 마스크와 좌표 포함 관계 확인
(4) 정보 반환: 객체 발견 시 mask_id, name, description 반환
(5) LLM 설명 생성: API 레이어에서 1문장 설명 자동 생성

7.5 데이터 저장 구조
- vision/masks/작품명/array/: 세그멘테이션 마스크 (.npy 파일)
- vision/masks/작품명/contour/: 컨투어 정보 (JSON 파일)
- vision/mask_annotation/작품명.json: 마스크 이름 및 설명
- vision/boxes/작품명.json: 초기 바운딩 박스 정보
- vision/visualizations/: 객체 인식 결과 시각화 이미지

7.6 정확도 보장 요소
- 초기 바운딩 박스 어노테이션의 정확도
- 설명할 가치가 있는 객체의 적절한 선별
- 마스크 이름 및 설명의 일관된 어조 유지
- LLM 설명 생성 시 TTS 최적화 적용


8. 시스템 실행 방법
========================================

8.1 사전 준비
시스템 실행 전 다음 사전 준비가 필요합니다.

(1) 패키지 설치
- 명령어: pip install -r requirements.txt
- 주요 패키지: fastapi, uvicorn, openai, numpy, scikit-image, Pillow

(2) 환경 변수 설정
- OpenAI API 키 설정 필요
- 설정 방법:
  * 터미널: export OPENAI_API_KEY=your_api_key_here
  * 또는 .env 파일 생성

8.2 서버 실행 절차
(1) API 서버 실행: python api.py
- 실행 주소: 0.0.0.0:14723
- 로컬 접근: http://localhost:14723

(2) 외부 접근 활성화: bash ngrok.sh (별도 터미널)
- ngrok이 생성하는 동적 URL로 인터넷 접근 가능

8.3 테스트 방법
- API 테스트: python client.py 실행
- API 문서 확인: http://localhost:14723/docs (Swagger UI)


9. 주요 파일 설명

9.1 핵심 모듈

api.py
- 역할: FastAPI 기반 메인 API 서버

curation_types.py

touch_recognition.py

client.py
- 역할: API 테스트 클라이언트

10. 개발 시 주의사항
========================================

10.1 큐레이션 타입 개발 규칙
큐레이션 타입을 수정하거나 추가할 때 다음 규칙을 준수해야 합니다.

(1) TTS 최적화 필수 준수
- 따옴표, 괄호, 특수기호 사용 금지
- 종결어미: 반드시 니다 체 사용
- 작품명: 한국어 표기
- 문체: 자연스러운 구어체

(2) 분량 제약 준수
- 타입별 정해진 문장 수 및 글자 수 반드시 준수
- 프롬프트에 분량 제약 명확히 명시

(3) 테스트 필수
- 프롬프트 수정 후 client.py를 통한 다양한 케이스 테스트 수행

10.2 새 작품 추가 절차
새로운 작품을 추가할 때는 다음 단계를 순차적으로 진행합니다.

(1) 기본 데이터 준비
- 작품 이미지: vision/artwork_images/, assets/artwork_images/에 추가
- 작품명 등록: curation_types.py의 ARTWORK_NAMES 및 ARTWORK_NAME_KR_TO_EN에 추가
- 설명 텍스트: assets/llm/document/에 파일 생성

(2) 비전 인식 데이터 구축
- 바운딩 박스 어노테이션: get_box.py 실행
- 세그멘테이션 마스크 생성: box_to_seg.py 실행
- 컨투어 변환: contour_visualize.py 실행
- 마스크 어노테이션: vision/mask_annotation/에 JSON 파일 생성
- 테스트: contour_gui.py로 확인

(3) 비교 데이터 추가
- transformed_pair.json에 다른 작품과의 공통점 및 차이점 정보 추가

10.3 성능 최적화
API 응답 시간 최적화를 위해 다음 사항을 고려합니다.

(1) 캐싱
- 마스크 데이터는 최초 로드 시 메모리 캐싱
- 서버 재시작 시 캐시 초기화됨

(2) LLM 응답 시간
- OpenAI API 호출 시간이 응답 시간의 대부분 차지
- 필요 시 더 빠른 모델 사용 또는 응답 캐싱 전략 고려

(3) 비동기 처리
- 대량의 터치 인식 요청 예상 시 비동기 처리 고려

10.4 에러 처리 규칙
- 400 Bad Request: 클라이언트의 잘못된 요청
- 422 Unprocessable Entity: 유효성 검증 실패
- 500 Internal Server Error: 서버 내부 오류
- 모든 에러 응답: detail 필드에 명확한 에러 메시지 포함

10.5 보안 고려사항
- OpenAI API 키: 환경 변수로 관리, 코드에 직접 작성 금지
- ngrok 외부 URL: 공개적이므로 필요 시 인증 메커니즘 추가 고려


11. 문제 해결
========================================

11.1 서버 시작 실패
확인 사항:
- OpenAI API 키 설정: 환경 변수 OPENAI_API_KEY 확인
- 포트 충돌: 14723 포트 사용 중인 다른 프로세스 확인 및 종료
- 패키지 설치: requirements.txt의 모든 패키지 설치 여부 확인

11.2 LLM 응답 이상
확인 사항:
- 프롬프트 파일 내용 검토 및 수정
- memory 파라미터 전달 여부 확인
- 작품명 정확성 확인 (정확한 한국어 표기)
- 테스트: client.py 실행으로 다양한 케이스 확인

11.3 터치 인식 실패
확인 사항:
- 마스크 데이터 존재 여부: vision/masks/작품명/array, contour 디렉토리 확인
- 마스크 어노테이션: mask_annotation/작품명.json 파일 확인
- 좌표 형식: 0-1 사이의 정규화된 값인지 확인
- 시각적 확인: contour_gui.py 실행

11.4 작품 비교 기능 오류
확인 사항:
- 비교 데이터 존재: transformed_pair.json에서 해당 작품 쌍 확인
- 키 형식: 작품1-작품2 또는 작품2-작품1 형식 확인
- 파라미터 전달: related_artwork 파라미터 확인

11.5 ngrok 연결 실패
확인 사항:
- ngrok 설치 여부
- 인증 토큰 유효성: ngrok.sh의 토큰 확인
- API 서버 실행 여부: 서버가 먼저 실행되어 있는지 확인
- URL 접근 테스트: ngrok 생성 URL 접근 가능 여부 확인
